# GitOrange from npm Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `npx gitorange install|upgrade|adopt|status` installs and upgrades GitOrange from a published npm package,
with no checkout, and `yarn release:publish vX.Y.Z` publishes a GitOrange release to npm from the operator's machine.

**Architecture:** The installer in `scripts/gitorange/` stops assuming a checkout: a `Source` (checkout or package)
says where the template, migrations, build and runner image context are, what version they are, how to run wrangler
and which command to print. The package is the installer bundled by esbuild plus the prebuilt worker, assets,
migrations and `actions/runner/`; each install's config is generated under `~/.gitorange/<slug>/` with absolute paths
into the package. `upgrade` and `adopt` are new commands over the same state, plan and step functions.

**Tech Stack:** TypeScript (Node type stripping in-repo; esbuild bundle for the package), vitest (node), jsonc-parser,
@clack/prompts, wrangler (pinned), Cloudflare REST, Docker (for deploys), npm.

**Spec:** `docs/superpowers/specs/2026-10-19-npm-cli-design.md` (approved 2026-10-21).

**Blueprint (read, don't re-derive):** saasmail's finished implementation of the same plan —
`~/workspace/saasmail-install/scripts/saasmail/` (`source.ts`, `home.ts`, `versions.ts`, `upgrade.ts`, `adopt.ts`,
`adopt-worker.ts`, `public-dns.ts`, `pack.mjs`, `smoke-config.ts`, `globals.d.ts`, and their tests) and its plan
`~/workspace/saasmail-install/docs/superpowers/plans/2026-10-17-npm-cli.md`. Each task names the saasmail file it
ports. Port behaviour, messages and tests, renamed (`saasmail` → `gitorange`, `SAASMAIL_*` → `GITORANGE_*`), and adapt
only where this plan says GitOrange differs.

**Branch:** `npm-cli` (on `main`, holds the spec). PR to `main` on git.xyspace.dev when done.

## Global Constraints

- yarn only for project commands; `npm` only inside `release:publish` and the package smoke test. Never commit
  `wrangler.jsonc`. Never hand-write migrations (this plan adds none).
- CLI tests: `yarn vitest run --config scripts/gitorange/vitest.config.ts`; `yarn typecheck` clean; `yarn format`
  before each commit. Imports inside `scripts/gitorange/` use `./x.ts` (`erasableSyntaxOnly`: no enums, parameter
  properties or namespaces). Code style: the repo's (single quotes; prettier decides).
- No Cloudflare, GitHub or npm call without the injected `fetchImpl` / `Cloudflare` port; tests never touch the
  network.
- Package name `gitorange`, bin `gitorange`. State home `~/.gitorange`, overridden by `GITORANGE_HOME`; dirs 0700,
  files 0600.
- Package Node floor = wrangler's (`>=22.0.0`), in its `engines`; the in-repo floor stays `package.json`'s `>=22.18`.
- Wrangler in the package is pinned exactly to the repo's installed version (read `node_modules/wrangler/package.json`
  at pack time).
- Secrets: only names missing on the worker are ever generated or sent; the secrets file never contains an existing
  name. `upgrade` never adds `SETUP_CODE_HASH`. Never print a secret.
- Operator-typed secrets (`R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY`, `CF_ANALYTICS_TOKEN`) never block an upgrade: in
  a terminal, the same masked prompt and check as install (skippable); with `--yes`, deploy without and list them as
  missing with the command that adds them later. Pasted values are not part of the plan digest.
- Docker: commands that deploy (`install`, `upgrade`, and `--resume` of either) check it in preflight, before the plan
  and before writing. Not installed (`docker` not on PATH): `Docker is not installed. GitOrange runs Actions jobs in
containers, and deploying builds the runner image with Docker. Install Docker Desktop
(https://docs.docker.com/get-docker/), start it, then run the same command again.` Installed but not answering
  (`docker info` fails): `Docker is installed but not running. Start Docker Desktop (or the Docker daemon), then run
the same command again.` `adopt` and `status` never check Docker.
- GitHub repo for version comparison: `choyiny/gitorange`. npm registry URL: `https://registry.npmjs.org/gitorange`.
- Printed commands come from `source.command(...)`: checkout → `yarn gitorange <args>`, package →
  `npx gitorange@<version> <args>`.
- Wrangler always runs from the install's own config directory with `--config <configDir>/wrangler.jsonc` in package
  mode (never from a checkout's directory).
- Commit messages end with the session's attribution lines.

## Review Focus

1. Running a later `npx gitorange@X` changes every package path in the generated config, including the runner
   Dockerfile path: that alone is neither "hand-edited" nor drift (Task 3 test `package path change is not drift`).
2. An upgrade killed after migrations and before deploy: `--resume` skips the migrations and deploys (Task 7 test
   `resume after failed deploy skips migrations`).
3. The adopted worker's Durable Object classes (declared through `exports` with SQLite storage) must deploy unchanged:
   the generated config lists exactly the classes the template has, and the plan stops if the deployed worker has a DO
   class the template lacks (Task 9 test `unknown durable object class stops`).
4. Adopting `git.xyspace.dev`-shaped workers whose Artifacts namespace or containers app cannot be confirmed by the
   API: accepted, shown as `bound, not verified` (Task 9 test `unverifiable binding is reported, not a stop`).
5. `release:publish` run from a dirty working copy or on a version already on npm: refuses before building, and never
   reads the working copy's files (Task 12 tests).
