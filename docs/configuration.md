# Configuration

GitOrange reads its configuration from `wrangler.jsonc` (copied from [`wrangler.jsonc.example`](../wrangler.jsonc.example), gitignored) and from Worker secrets. **Site admin → Setup** checks all of it on the running worker (secrets set and long enough, bindings present and reachable, variables, migrations, AI Gateway) and shows how to fix what's wrong.

## Bindings

Binding names are load-bearing — the worker looks them up by exact name. Resource names and IDs can be anything.

| Key                               | Required value       | What it is                                                                                                                                                                                                                                                                         |
| --------------------------------- | -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `d1_databases[].binding`          | `"DB"`               | Users, invitations, tokens, repositories, pull requests, comments                                                                                                                                                                                                                  |
| `artifacts[].binding`             | `"ARTIFACTS"`        | Git storage. `namespace` groups this instance's repositories                                                                                                                                                                                                                       |
| `send_email[].name`               | `"EMAIL"`            | Outbound invitation and email-verification mail via Cloudflare Email Sending                                                                                                                                                                                                       |
| `r2_buckets[].binding`            | `"LFS"`              | Git LFS file contents, keyed `lfs/<repository id>/<oid>`                                                                                                                                                                                                                           |
| `r2_buckets[].binding`            | `"ACTIONS_LOGS"`     | Actions step logs, keyed `actions/<repository id>/<run>/<job>/<step>.log`                                                                                                                                                                                                          |
| `r2_buckets[].binding`            | `"ACTIONS_CACHE"`    | The Actions cache (`actions/cache`, `setup-node`'s `cache:`): zstd tarballs keyed `actions-cache/<repository id>/<ref>/<key>.tar.zst`. Runners reach it through pre-signed URLs, so the R2 API token must cover this bucket too. Give it a 7-day lifecycle rule                    |
| `workflows[].binding`             | `"ACTIONS_RUN"`      | One Workflow instance per Actions run (`class_name: "ActionsRun"`)                                                                                                                                                                                                                 |
| `durable_objects.bindings[].name` | `"JOB_RUNNER"`       | One `JobRunner` Durable Object per Actions job; it owns the job's container                                                                                                                                                                                                        |
| `durable_objects.bindings[].name` | `"ACTIONS_QUEUE"`    | One `ActionsQueue` Durable Object: the instance's queue of Actions jobs. At most **Site admin → Settings → Jobs running at once** (default 10) job containers run at a time; the rest wait, first come first served. Without it jobs start as soon as they're ready, with no limit |
| `durable_objects.bindings[].name` | `"MERGE_RESOLVER"`   | One `MergeResolver` Durable Object per AI conflict resolution: a Cloudflare Computer workspace and the pi agent                                                                                                                                                                    |
| `durable_objects.bindings[].name` | `"LIVE"`             | One `LiveHub` Durable Object: the WebSocket hub that tells open pages to refresh (it relays pings and stores nothing). Without it pages still work, they just don't update live                                                                                                    |
| `workflows[].binding`             | `"MERGE_RESOLUTION"` | AI conflict resolution and reviews: one instance per resolution attempt or reviewed commit, plus a sweep per push or merge (`class_name: "MergeResolutionWorkflow"`)                                                                                                               |
| `ai.binding`                      | `"AI"`               | Workers AI: conflict resolution, reviewer agents' reviews, and Clef for `gitorange/relevance@v1`, through AI Gateway (`AI_GATEWAY`)                                                                                                                                                |
| `assets.binding`                  | `"ASSETS"`           | The built React app in `dist/client`                                                                                                                                                                                                                                               |

`containers` defines the Actions runner: class `JobRunner` with `scheduling_policy: "durable_object"` and one image named `runner`, built from [`actions/runner/Dockerfile`](../actions/runner/Dockerfile) when you deploy (Docker must be running). Each job picks its instance size at start from `runs-on` (`ubuntu-latest` → `standard-2`, 1 vCPU, 6 GiB, 12 GB disk; `gitorange-standard-1` … `gitorange-standard-4` pick a size; `runs-on` may be an expression over the `github` and `matrix` contexts, so a workflow shared with GitHub can pick a GitOrange size only here). Jobs run on the image's preinstalled Node.js: `setup-node` doesn't download another version. To deploy without Actions, remove the `JobRunner` container, its Durable Object binding and export, the `ActionsQueue` Durable Object binding and export, the `ACTIONS_RUN` Workflow, and the `ACTIONS_LOGS` bucket. Without them, pushes never queue runs and the Actions tab says Actions isn't set up. To deploy without AI conflict resolution and reviews, remove the `MergeResolver` Durable Object binding and export and the `MERGE_RESOLUTION` Workflow: conflicts then have to be resolved locally, agents never review, and a person approves every pull request.

Keep `assets.run_worker_first` as shipped (it includes `/mcp` and `/.well-known/*`, which the MCP server and OAuth discovery need): the git endpoint (`/<owner>/<repo>.git/...`) and `/api/*` must reach the worker before static asset handling.

## Variables

Variables marked **Default only** are defaults: **Site admin → Settings** overrides them, stored in D1 (`instance_settings`), and takes effect without a deploy. They're read only where they're used (invitations, reviews, the MCP handshake, page loads), never on every request. Deploy-time facts (`BASE_URL`, the R2 account, and bucket names, which must match the bindings) stay here only.

| Variable                    | Example                     | Purpose                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| --------------------------- | --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `APP_NAME`                  | `GitOrange`                 | The instance's name: page titles, sign-in and setup pages, invitation emails, the git auth realm, AI agent prompts, and the MCP server (whose id is the lowercased name, e.g. `XY Space Git` → `xy-space-git`) **Default only:** a site admin can change it in **Site admin → Settings** without a deploy.                                                                                                                                                      |
| `BASE_URL`                  | `https://git.example.com`   | Public origin; used for auth and trusted origins. Cookies are `Secure` when this is `https://`                                                                                                                                                                                                                                                                                                                                                                  |
| `FROM_EMAIL`                | `noreply@example.com`       | Sender for invitation and verification emails; its domain must be onboarded to Email Sending **Default only:** a site admin can change it in **Site admin → Settings** without a deploy.                                                                                                                                                                                                                                                                        |
| `R2_ACCOUNT_ID`             | `0123…cdef`                 | Account that owns the LFS bucket; pre-signed URLs point at `https://<R2_ACCOUNT_ID>.r2.cloudflarestorage.com`                                                                                                                                                                                                                                                                                                                                                   |
| `AI_GATEWAY`                | `default`                   | AI Gateway every Workers AI call goes through, so its logs and analytics show requests, tokens, and cost. Requests are tagged with metadata `feature` (`review-summary`, `review-trigger`, `review-agent`, `merge-resolution`, `stack-decide`, `stack-explain`, `ci-relevance`), `instance`, and `classification` where it applies. `default` is created automatically on first use; any other name must exist in the account. `off` calls Workers AI directly. |
| `RESOLVER_MODEL`            | `@cf/zai-org/glm-5.3`       | Workers AI model the conflict-resolution agent uses; it must support tool calling **Default only:** a site admin can change it in **Site admin → Settings** without a deploy.                                                                                                                                                                                                                                                                                   |
| `SUMMARY_MODEL`             | `@cf/zai-org/glm-5.3-flash` | Reviews: writes the one-line summary of each changed file ([Reviewer agents](auto-merge.md)) **Default only:** a site admin can change it in **Site admin → Settings** without a deploy.                                                                                                                                                                                                                                                                        |
| `REVIEW_MODEL`              | `@cf/zai-org/glm-5.3`       | Reviews: each reviewer agent's single-pass review (Clef decides which agents review). **Default only:** a site admin can change it in **Site admin → Settings** without a deploy.                                                                                                                                                                                                                                                                               |
| `LFS_BUCKET_NAME`           | `gitorange-lfs`             | The LFS bucket's name; must match `r2_buckets[].bucket_name` (a binding doesn't expose its name)                                                                                                                                                                                                                                                                                                                                                                |
| `ACTIONS_CACHE_BUCKET_NAME` | `gitorange-actions-cache`   | The Actions cache bucket's name; must match the `ACTIONS_CACHE` binding's `bucket_name`. Without it (or the R2 token secrets), jobs run without a cache                                                                                                                                                                                                                                                                                                         |

### Usage & cost

Site admin → **Usage & cost** shows what this deployment uses on Cloudflare and what it would cost. GitOrange records Actions runner time, Workers AI calls, and emails itself. Everything else comes from Cloudflare's GraphQL Analytics API, which a daily cron (`triggers.crons`: `30 2 * * *`, 02:30 UTC) pulls into D1. Every query is filtered to the resources named below, so other things on the account never show up as GitOrange's. Leave a variable empty to skip that metric; it then shows as "not configured".

| Variable                         | Example                      | Purpose                                                                                                             |
| -------------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `WORKER_NAME`                    | `gitorange`                  | This Worker's script name (the top-level `name`), for Workers requests and CPU time                                 |
| `D1_DATABASE_ID`                 | `xxxxxxxx-xxxx-…`            | The `DB` database's `database_id`, for rows read and written and storage                                            |
| `ACTIONS_LOGS_BUCKET_NAME`       | `gitorange-actions-logs`     | The `ACTIONS_LOGS` bucket's name. With `LFS_BUCKET_NAME` and `ACTIONS_CACHE_BUCKET_NAME`, the R2 buckets to measure |
| `ARTIFACTS_NAMESPACE`            | `gitorange`                  | The `artifacts[].namespace`, for Artifacts operations                                                               |
| `ACTIONS_WORKFLOW_NAME`          | `gitorange-actions-run`      | The `ACTIONS_RUN` Workflow's `name`                                                                                 |
| `MERGE_RESOLUTION_WORKFLOW_NAME` | `gitorange-merge-resolution` | The `MERGE_RESOLUTION` Workflow's `name`                                                                            |
| `JOB_RUNNER_NAMESPACE_ID`        | `0123…cdef`                  | Durable Object namespace ID of `JobRunner`: dashboard → Durable Objects → the class; the ID is on its page          |
| `MERGE_RESOLVER_NAMESPACE_ID`    | `0123…cdef`                  | Same, for `MergeResolver`                                                                                           |
| `LIVE_NAMESPACE_ID`              | `0123…cdef`                  | Same, for `LiveHub`                                                                                                 |

`R2_ACCOUNT_ID` is the account the queries read, and `AI_GATEWAY` names the gateway whose request count is shown (for the whole gateway, which other apps or a dev instance may share, so it is never added to GitOrange's totals).

The figures are estimates, not an invoice:

- Prices live in one table, [`worker/src/usage/pricing.ts`](../worker/src/usage/pricing.ts), with the date they were last checked and their sources. Costs are computed on read, so fixing a price re-prices history.
- Included allowances and the $5 plan fee are per Cloudflare account. The page shows GitOrange's usage at list price and the cost if GitOrange had the allowances to itself. If other things run on the account, the real bill for GitOrange's usage falls between the two.
- Containers: memory and disk are billed on the provisioned instance size, so runner time × size is exact. vCPU is billed on active use, so runner time × vCPUs is an upper bound. Workers AI is billed in neurons. The page prices recorded token counts at Cloudflare's per-model rates.
- Not measured: Artifacts storage, Workflows storage, container egress, and Workers Logs events, which have no analytics dataset. Some Durable Objects, Workers CPU, Artifacts, and AI Gateway cost fields are not in Cloudflare's docs yet. If Cloudflare rejects one, only that metric shows as unavailable, with the reason.
- The cron re-reads the last three days, since analytics settle late. It also fills in up to four older days each run, so a new install has the last 30 days (Cloudflare's retention) after about a week. **Sync now** re-reads today and the last three days.

## Secrets

| Secret                                     | How to set                                                                                                                                                                                                                                                              |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BETTER_AUTH_SECRET`                       | Signs sessions and encrypts the MCP server's OAuth signing keys; changing it signs everyone out and disconnects every MCP app. Production: `wrangler secret put BETTER_AUTH_SECRET`. Local: `.dev.vars` (see `.dev.vars.example`). Generate with `openssl rand -hex 32` |
| `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` | S3-compatible credentials of an R2 API token with **Object Read & Write** on the LFS bucket, used only to sign short-lived LFS URLs. Without them Git LFS answers "not configured"; everything else works                                                               |
| `CF_ANALYTICS_TOKEN`                       | Optional. An account API token with only **Account Analytics: Read**, for Usage & cost. Production: `wrangler secret put CF_ANALYTICS_TOKEN`. Without it, the page shows only what GitOrange records itself (Actions runners, Workers AI calls, emails)                 |

## Environments

The top level of `wrangler.jsonc` is production (`yarn deploy`). The `env.dev` block is what `yarn dev` runs: a local D1 database, and Artifacts in a separate `gitorange-dev` namespace (Artifacts has no local emulator), so development never touches production repositories. Likewise, dev LFS files go to a separate `gitorange-lfs-dev` bucket (a real one, since pre-signed URLs must reach R2). Actions jobs in dev run in local Docker containers, so Docker must be running for `yarn dev`, and their logs go to a local R2 bucket.

## Cron Triggers

`triggers.crons` (`"17 4 * * *"`, daily) runs housekeeping: it deletes Actions runs that finished more than **Site admin → Settings → Keep Actions runs for** days ago (default 90, or keep forever), with their jobs, steps, and step logs in R2. Queued and running runs are never touched. Site admin shows when it last ran and how much it deleted.
